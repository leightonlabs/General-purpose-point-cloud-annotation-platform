## 1. 最终目标、约束与阶段划分

### 1.1 最终目标

一个统一的点云标注平台：公共点云底座 + 可复用的作业能力模块 + 按项目配置的规范 + 数据格式适配器，覆盖下列能力域，而不是为每个甲方单独开发一套平台。

| 能力域 | 最终要具备的能力 |
|---|---|
| 数据接入 | 任务包（一包多帧）；常见格式与自定义 BIN 布局；单帧、连续帧、多站、融合地图；附带图像、标定、位姿、时间戳 |
| 显示与浏览 | 多种着色、裁剪、三视图、鸟瞰、合并帧、相机图像联动、大场景分块与 LOD |
| 目标与轨迹 | 立方体、跨帧轨迹（传播、插值、关联修正）、俯仰 / 横滚 |
| 点级标注 | 语义分割（刷点）、实例分割、全景分割、时序实例 |
| 多传感器 | 3D 框投回图像、多雷达合并、跨传感器结果对到同一轨迹 |
| 道路与地图要素 | 车道中心线与拓扑（连接、相邻、灯控车道）、三维折线 / 区域 |
| 占用 | 占用格子（空 / 占 / 未知、静止 / 运动、类别） |
| 其它任务族 | 关键点与骨架、刚体位姿、帧级分类与事件 |
| 规范与流程 | 类别、属性、类别控件、工具与质检规则配置；自定义快捷键；保存恢复、冲突处理、质检、返工、验收统计 |
| 交付 | 通用训练包 + 各甲方格式适配器；大规模异步导出 |
| 智能辅助 | 预标导入、模型预标、2D 掩码辅助 3D 分割、质检规则自动检查 |

### 1.2 开发约束

1. 代码只落在点云模块的路径内：前端 `labeling-admin-web/src/workbench/editors/lidar/`、`labeling-admin-web/tests/pointcloud/`；后端 `com.pmsm.zs.labeling.pointcloud` 包、`resources/mapper/pointcloud/`、对应测试目录、`labeling_pointcloud_migrate.sql`（[07 §1.1](./07-研发规范与一期计划.md#11-允许修改的路径)）。测试工具（测试包生成器、端到端脚本、导出校验脚本）放在本仓库 `tools/`。
2. 平台已有能力（任务、派工、权限、规范库、结算、对象存储、数据导入）**只调用不修改**；依赖清单见 [07 §1.2](./07-研发规范与一期计划.md#12-对外依赖清单只调用不修改)。
3. 其它模块中尚未完整实现或仅为占位的组件不复用，点云需要的能力在点云模块内自建。
4. 需要其它模块配合的事项列入对接清单（[07 §7](./07-研发规范与一期计划.md#7-与伙伴模块的对接事项)），由对应负责人决定。
5. 后续各阶段的设计均以“不改其它模块也能交付”为前提；需要伙伴配合的部分只作为可选优化。

## 7. 推荐方案要点

1. **作业单元改为任务包**：一个样本 = 一个任务包，用 `package.json` 描述多帧、相机、标定与位姿，借平台既有的 OSS 键清单导入登记，平台导入、派工、结算都不用改（D17）。
2. **页面按参考结构重构，按实际功能取舍**：去掉包间队列，包内切帧预取；保持现有深色配色（D16、D22）。
3. **规范库只用可用部分**：类别、属性、版本照用；控件类型、关系类型、占用状态、快捷键放在点云配置与作业台（D18、D19）。
4. **先交付可测试链路**：阶段 1 第 3 周末（M1a）就让测试人员用合成测试包走通全链路，此后每个阶段以“链路准出”为完成标志。
5. **按依赖排控件**：立方体、刷点先迁入并增强；相机投影与 4D 共用标定、位姿、多帧，一起做；车道依赖鸟瞰与合并帧；占用格子依赖刷点与轨迹，放在最后（D20）。
6. **协议只增不改**：每帧结果沿用阶段 0 字段，新增包级与帧级结构，编码沿用 `rle-varint-v1`，阶段 0 数据无需迁移。
